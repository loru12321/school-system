## Optimizations Implemented

### Content-Hashed Bundles Now Served Immutable via `_headers` ✅
**Impact**: boot-runtime / service-worker-runtime / sw-runtime / style bundles
now served `public, max-age=31536000, immutable` from Cloudflare's edge —
eliminating revalidation round-trips on every page load of versioned assets.

## Why the Fix Had to Live in `_headers`, Not the Worker

Empirically established on production (2026-08-22):

| Path | Header served | Worker policy (`getStaticAssetCacheControl`) |
|---|---|---|
| `/icon.svg` | `public, max-age=86400` (from `_headers`) | `public, max-age=3600, s-w-r=86400` — **ignored** |
| `/assets/js/boot-runtime-*.js` | `no-store` (from `/assets/js/*` rule) | `immutable` — **ignored** |
| `/robots.txt` | (no cache-control; worker-passed) | `''` |

The Cloudflare Workers+Assets platform serves static assets from its own edge
cache with `Cache-Control` computed from platform defaults + `public/_headers`
rules. Worker-side header overrides on `env.ASSETS.fetch` responses never reach
clients for static assets. `_headers` rules are merged (an inherited header is
joined with a comma, not replaced) — so a sibling rule's `no-store` always won
over the immutable rule unless detached.

### Root Cause: Two-Wildcard Rule Never Matched
The pre-existing `/assets/js/*runtime*.js → immutable` rule (with two `*` splats)
**never matched** on the platform: production boot-runtime responses carried the
`/assets/js/*` catch-all's `no-store` + `CDN-Cache-Control: no-store` even for
fresh rotated URLs. Replaced with explicit single-splat rules per family:

```text
/assets/js/boot-runtime-runtime-*.js
  ! Cache-Control
  ! CDN-Cache-Control
  ! Cloudflare-CDN-Cache-Control
  Cache-Control: public, max-age=31536000, immutable

/assets/js/service-worker-runtime-runtime-*.js   (same detach + immutable)
/sw-runtime-*.js                                  (same detach + immutable)
```

The `!` detach strips the inherited no-store headers from the `/assets/js/*`
catch-all before setting immutable — the documented override for header merging.

## Technical Notes

### Edge Cache Behavior
- Workers+Assets pre-warms/caches assets at deploy time: a freshly-uploaded URL
  serves `CF-Cache-Status: HIT` on its first fetch, with headers computed from
  the current `_headers` rules.
- Edge cache key ignores query strings; no purge path exists (no `wrangler cache
  purge`; OAuth token lacks `zone:purge_cache`). **Deploying wrong `_headers`
  rules permanently poisons cached responses for a given URL** — re-verify
  rules before every deploy that touches `_headers`.
- Fresh content hashes (`0cd8cb68c6a9`) give clean URLs for verification; orphan
  URLs from prior rotations retain stale headers but are unreferenced.
